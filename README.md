### CookieCapes account deployment

CookieAPI must be upgraded before this website. Configure `WEBSITE_SERVICE_TOKEN`
with the API's dedicated website service credential and `COOKIECAPES_API_URL` with
its origin; never expose credentials through `NEXT_PUBLIC_` variables.
Set `NEXT_PUBLIC_COOKIECAPES_API_URL` to the public API origin before building
(for production, `https://api.cookieattack.de`); this value contains no secret.
Auth.js now uses CookieAPI-backed database sessions and internal user UUIDs.
Existing website JWT sessions require signing in again. Discord IDs remain linked
identity metadata for `ADMIN_DISCORD_IDS` and the separate homepage registration.
Do not enable email-based automatic OAuth account linking for future providers.

Register the exact MC-ID redirect URI
`https://YOUR-WEBSITE/cookiecapes/account/minecraft/callback` in CookieAPI and at
MC-ID. Linking stays unavailable when the API reports `mcid_enabled: false`.
CookieAPI performs OIDC verification and enforces upload/review authorization;
the browser receives neither provider secrets nor the service credential.

The account page provides explicit legacy review and 30-day recovery. Blue badges
mean a linked owner uploaded or claimed a cape; orange badges mean a verified
Minecraft session uploaded it. Neither badge establishes artwork authorship.
Private cape previews use an authenticated, non-cacheable website proxy.

For local end-to-end testing of all three repositories, see
[the workspace testing guide](../CookieAPI/docs/local-testing.md).

### CookieCapes public preview images

Public cards use transparent 384×512 PNGs generated by the website's Node.js
runtime with `sharp`. Failed card images load a 3D viewer on demand; if that also
fails, the card shows "Cape couldn't load". Healthy images allocate no WebGL
contexts. Interactive detail views use static images after WebGL failure;
if those images also fail, they show the error message without retrying 3D.
Private previews, editors and `/stats` keep their existing viewers.

The image routes are
`/api/cookiecapes/previews/capes/{id}` and
`/api/cookiecapes/previews/players/{uuid}`. The optional `edited` query versions
cape edits. Player images resolve the current cape server-side; historical skins
accept a hexadecimal `skin` texture hash and optional `slim=true|false`.
Use the helpers in `app/cookiecapes/lib/preview-url.ts` to build URLs.

Cape metadata and poster PNGs come from `NEXT_PUBLIC_COOKIECAPES_API_URL`,
without authentication. Current skins use Minotar and historical textures use
Crafthead, matching the existing viewers. Redirects and caller-provided URLs are
rejected. Downloads are limited to 2 MiB (metadata: 64 KiB), PNG dimensions to
4096×4096, and the shared source deadline to eight seconds. Geometry preparation
has a 2.5-second budget and individual native image operations a two-second timeout.
The default route renders static PNG posters, including animated capes.
With `animated=1`, public animation manifests/pages are projected using the same
renderer and returned as a looping 192?256 WebP. Cards request this only on hover
or keyboard focus while visible, and respect reduced motion. Animation failures
keep the poster; interactive detail views retain full animation playback.
Long timelines sample at most 48 source frames, preserving the overall loop duration;
short timelines retain frame timing to the nearest millisecond. Each animation
generation has a 14-second request deadline, a 10-second projection budget and
one concurrent worker per process. Compressed results use a 24 MiB/16-entry, one-hour
cache; pages are limited to 16 MiB and 2048?2048 pixels. Visibility is checked before
using cached output, and animation URLs are constructed from trusted API paths. Source texture details survive projection, including
HD textures, skin overlays, classic/slim arms and mirrored legacy limbs.

Successful responses require browser revalidation and set
`Vercel-CDN-Cache-Control: public, s-maxage=3600, must-revalidate`.
Skin downloads may cache for one hour; cape visibility and textures are fetched
fresh on generation. Players with no cape (`null`, `-1` or `0`) render their skin
normally. Stale/private cape selections render the skin alone with `no-store`
so an incomplete outfit cannot enter the CDN. Image errors also return `no-store`
and trigger the card's 3D fallback. Removed/private artwork may remain in the CDN for one hour;
skin changes may take an hour. Cache misses regenerate the PNG.
Failed HTTP downloads preserve their original status even if aborting the body
causes cleanup to reject. Already-failed images are checked after hydration so
their error event cannot be missed before React attaches its handlers.
A centered spinner remains visible until each image loads, including after a
source change; images that loaded before hydration clear the spinner immediately.
